## 1. 핵심 원칙

SFANDOM은 정적 사이트다. 정기 점검에서 발견한 문제를 곧바로 코드에 적용하면 작은 변경도 서로 겹치며 사이트가 꼬일 수 있다. 따라서 매일 새벽 자동 작업의 권한은 **읽기 전용 점검·분석·기록·보고**로 제한한다.

자동 작업은 다음 행위를 절대 수행하지 않는다.

- 코드·콘텐츠·설정·데이터·자산 수정
- 파일 생성·이동·이름 변경·삭제
- 찌꺼기 제거 또는 코드 정리의 실제 적용
- 브랜치·커밋·PR 생성
- 병합·배포·롤백
- GitHub Pages 또는 워크플로 설정 변경
- 캐시 버전 변경
- 오류를 고치기 위한 hotfix나 임시 패치
- 문제 발견을 이유로 한 자동 정상화

문제 발견 시 할 일은 **원인과 영향 범위를 분석하고 수정 후보를 제안하여 보고하는 것까지**다. 실제 수정은 Ji의 별도 명시적 승인 이후 독립된 작업에서만 수행한다.

## 3. 04:00 실행 순서

1. 현재 라이브 사이트와 `main` 상태를 읽기 전용으로 확인한다.
2. 주요 페이지, 코드 참조 관계, GitHub Pages 및 워크플로 상태를 점검한다.
3. 오류·경고·중복·고아 코드·찌꺼기 후보를 식별한다.
4. 각 항목의 증거, 위치, 원인, 영향 범위, 위험도를 기록한다.
5. 실제 사용 여부가 불확실하면 삭제 후보로 확정하지 않고 **확인 필요**로 분류한다.
6. 수정이 필요해 보여도 코드나 저장소에는 어떠한 변경도 하지 않는다.
7. 안전한 수정 방향, 예상 변경 파일, 검증 방법, 롤백 기준을 제안서로만 작성한다.
8. 오전 09:00 보고가 참조할 수 있도록 진단 결과를 남긴다.

## 4. 필수 점검 범위

- 라이브 사이트 접속 및 주요 페이지
- GitHub Pages와 관련 워크플로 상태
- `index.html`, CSS, JavaScript, `data/`, `assets/`, `archive/`
- HTML/CSS/JS 문법과 브라우저 콘솔 오류
- 깨진 내부·외부 링크, 이미지와 미디어 경로
- 중복 CSS/JS, 중복 이벤트 리스너, 미사용 import, 고아 코드 후보
- 임시 파일·빌드 산출물·숨은 잔여 데이터·캐시 버전 이상 후보
- 데스크톱 1440px 및 모바일 390px 반응형 화면
- 가로 스크롤, 잘림, 레이아웃 이동, 메뉴·채팅·콘텐츠 영역 이상
- 최근 변경 내역과 예상 밖 diff
- Archive와 과거 기사·픽·분석 기록의 참조 상태

모든 검사는 조회·렌더링·분석 범위에서만 수행한다.

## 5. 문제 분류

| 상태 | 기준 | 자동 작업 |
|---|---|---|
| 정상 | 확인된 이상 없음 | 정상 근거 기록 |
| 주의 | 잠재 문제이나 영향·원인이 불확실 | 관찰 항목과 추가 확인 방법 보고 |
| 오류 | 재현 가능한 기능·표시·참조 문제 | 원인·영향·수정 후보 보고 |
| 긴급 | 사이트 핵심 기능 장애 또는 광범위한 깨짐 | 즉시 긴급 보고, 코드 변경 금지 |
| 확인 불가 | 접근·권한·로그·렌더 검증 부족 | 정상 추정 금지, 사유 보고 |

오류나 긴급 상태여도 자동 수정·롤백·배포를 하지 않는다.

## 6. 찌꺼기·중복 코드 처리

새벽 작업에서는 찌꺼기와 중복 코드를 **후보로만 식별**한다. 실제 삭제하지 않는다.

후보 보고에는 다음을 포함한다.

1. 정확한 파일 경로와 위치
2. 저장소 전체 참조 검색 결과
3. HTML/CSS/JS/Event Listener/Import/Asset 연결 관계
4. 현재 페이지와 Archive 사용 여부
5. 삭제 시 예상 영향
6. 별도 수정 작업에서 필요한 검증
7. 복구 기준

용도나 참조 여부가 불확실한 항목은 삭제 후보가 아니라 **확인 필요**로 남긴다.

## 7. 보호 대상

- 정적 사이트의 CORE 구조
- 정상 작동 중인 HTML/CSS/JS와 공통 코드
- `main` 브랜치와 배포 상태
- Archive 및 보관함 경로와 데이터
- 과거 기사·픽·분석 기록
- Daily News, 카이로 콘텐츠, NEXT MATCH, Pick
- 공식 로고·캐릭터·브랜드 원본
- GitHub Pages·워크플로·도메인 설정
- 캐시 버전과 자산 경로

정기 점검은 위 대상을 수정하거나 재구성하지 않는다.

## 8. 실제 수정으로 전환되는 조건

다음 조건을 모두 충족해야 별도의 수정 작업을 시작할 수 있다.

1. 오전 09:00 보고서에 문제와 근거가 제시되었다.
2. 예상 수정 파일과 영향 범위가 명확하다.
3. 검증·복구 계획이 준비되었다.
4. Ji가 해당 수정 작업을 명시적으로 승인했다.
5. 정기 점검 자동화와 분리된 독립 작업으로 수행한다.

승인 전에는 브랜치·커밋·PR도 만들지 않는다.

## 10. 완료 판정

다음 조건을 모두 충족해야 점검 완료다.

- 필수 점검 범위와 결과가 기록되어 있다.

코드 또는 저장소에 변경이 발생했다면 해당 새벽 점검은 원칙 위반이며 완료로 처리하지 않는다.
